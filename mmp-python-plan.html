MMP on Python and Postgres

Decisions

What changes, and what survives intact

The v1.0 spec is architecturally sound and most of it carries over unchanged: the separation of a tracking edge from the business API, queue-buffered async ingestion, deterministic last-click attribution, hash-only API keys, and the honest scope split across Tiers A/B/C. Those are language-independent decisions and I am not relitigating them.

Two things change. Node/Fastify becomes Python, and — the more consequential call — ClickHouse comes out of the MVP. Running Postgres and ClickHouse from day one means two schemas, two retention policies, two failure modes, and a permanent consistency question between them, at a volume where one tuned Postgres is not close to breaking a sweat. Postgres with time-partitioned event tables and pre-aggregated rollups carries this product to roughly a billion rows per table before the read path becomes the constraint. The graduation trigger is defined in Scale, and the ingest layer is built so that adding a columnar sink later is a new consumer on an existing stream, not a rewrite.

The one place Python genuinely costs you

Per-request CPU on the click redirect is higher in Python than in Node, and the GIL means a worker process serves one request's Python bytecode at a time. The answer is architectural, not heroic: the redirect path executes almost no Python (cache read, UUID, one queue append), and you scale by process count — uvicorn workers sized to 2 × cores behind the load balancer. Budget for ~2× the instance count Node would need on the tracker tier. At MVP volumes that is one extra small instance, not a design problem.

Library choices worth defending

asyncpg, not psycopg-as-default

Binary protocol, native copy_records_to_table, roughly 3× psycopg2 on bulk paths. SQLAlchemy 2.0 async runs on top of it for the CRUD side, so there is one driver in the process.

Redis Streams for ingest

Consumer groups, acked delivery, replayable history, and a backlog you can actually see. Celery's opaque queue semantics and its pickle serializer are both liabilities here.

arq for outbound jobs

Async-native, small, Redis-backed. Postbacks and webhooks are IO-bound retry-with-backoff work — exactly its shape. No Celery, and therefore no pickle deserialization surface.

orjson + msgspec

orjson for serialization, msgspec for validating ingest payloads. Pydantic v2 stays on the business API where developer ergonomics matter more than microseconds.

uv + locked hashes

Dependencies resolved by uv into a hash-pinned lockfile, installed with --require-hashes. pip-audit gates CI. Supply chain is a security control, not a convenience.

PgBouncer, transaction mode

Hundreds of app connections collapse to tens of Postgres backends. Requires statement_cache_size=0 on asyncpg pools — a known footgun; encode it in the shared pool factory, not in each service.

Data

One Postgres, split into hot, warm and cold shapes

Three classes of table live in the same database with very different treatment. Business tables are small, mutable and fully constrained. Event tables are append-only, partitioned by day, and carry the minimum index set that the read path actually uses. Rollup tables are derived, rebuildable and the only thing the dashboard is allowed to query.

Business tables

Carried over from v1.0 essentially unchanged — users, organizations, organization_members, apps, api_keys, campaigns, tracking_links, integrations, provider_integrations, postback_rules, postback_deliveries, webhooks, consent_states, conversion_mappings. Every one gets organization_id, an RLS policy, and a foreign key with an explicit ON DELETE rule. UUIDv7 primary keys throughout, generated in Python, so index inserts stay time-local instead of scattering across the btree the way v4 does.

Event tables

Declarative range partitioning on the timestamp, one partition per day, created a week ahead by a scheduled job and dropped wholesale at retention. Retention by DROP TABLE costs nothing; retention by DELETE would generate hundreds of millions of dead tuples and hand autovacuum a problem it cannot win.

-- clicks: written by the click consumer in COPY batches
CREATE TABLE clicks (
  click_id          uuid        NOT NULL,      -- v7, minted at the edge
  clicked_at        timestamptz NOT NULL,
  organization_id   uuid        NOT NULL,
  app_id            uuid        NOT NULL,
  campaign_id       uuid,
  tracking_link_id  uuid        NOT NULL,
  device_hash       bytea,                    -- HMAC(gaid|idfa, daily pepper)
  ip_hash           bytea,                    -- HMAC(ip, daily pepper). raw IP never stored.
  country           char(2),
  platform          smallint,
  os_version        text,
  device_model      text,
  sub1 text, sub2 text, sub3 text,
  PRIMARY KEY (clicked_at, click_id)
) PARTITION BY RANGE (clicked_at);

-- per-partition indexes. deliberately few: every index is insert tax.
CREATE INDEX ON clicks_2026_09_07 (click_id);                       -- deterministic match
CREATE INDEX ON clicks_2026_09_07 (app_id, device_hash, clicked_at DESC)
  WHERE device_hash IS NOT NULL;                                 -- referrer/device match
CREATE INDEX ON clicks_2026_09_07 USING BRIN (clicked_at);         -- range scans, ~0 cost

-- events: same partitioning. dedup enforced by the unique key.

  received_at     timestamptz NOT NULL,        -- server clock. partition key. authoritative.
  occurred_at     timestamptz NOT NULL,        -- client clock. reported, never trusted.
  organization_id uuid        NOT NULL,
  app_id          uuid        NOT NULL,
  event_name      text        NOT NULL,
  anonymous_id    text        NOT NULL,
  user_id         text,
  session_id      uuid,
  platform        smallint,
  app_version     text,
  revenue_minor   bigint,                     -- integer minor units. never float.
  currency        char(3),
  properties      jsonb        NOT NULL DEFAULT '{}',
  PRIMARY KEY (received_at, app_id, event_id)
) PARTITION BY RANGE (received_at);

-- attributions: one row per install, immutable. corrections append, never update.
CREATE TABLE attributions (
  attribution_id  uuid PRIMARY KEY,
  app_id          uuid NOT NULL,
  install_key     text NOT NULL,        -- app_id + anonymous_id
  click_id        uuid,
  campaign_id     uuid,
  method          text NOT NULL,        -- referrer | click_id | organic
  attributed_at   timestamptz NOT NULL,
  window_days     smallint NOT NULL,
  superseded_by   uuid REFERENCES attributions(attribution_id),
  UNIQUE (app_id, install_key) WHERE superseded_by IS NULL
);

Why UNIQUE (app_id, install_key) is the most important line in the schema

"One install resolves to one attribution" is the invariant the whole product's numbers rest on. Enforcing it in application code means enforcing it in a worker that may be running four copies of itself against a queue that redelivers on timeout. Enforcing it as a partial unique index means the database refuses the duplicate no matter how many workers race, and the loser's ON CONFLICT DO NOTHING makes the race a non-event.

Rollup tables

The dashboard never touches events or clicks. It reads rollup_hourly and rollup_daily, keyed by (app_id, campaign_id, platform, country, event_name, bucket) with counters and revenue sums. A worker refreshes the trailing window every minute with an idempotent INSERT … ON CONFLICT DO UPDATE over a bounded time range, and re-refreshes the last 72 hours nightly so late events from offline SDK queues land in the reported numbers. The event explorer is the one screen allowed to hit raw partitions, always with a mandatory date range and a statement timeout.

Speed

Two hot paths, and nothing else is hot

Everything that matters for speed happens in two request handlers. The redirect decides whether users reach the app store, and the ingest endpoint decides whether the SDK's queue drains. Both are built to do a fixed, tiny amount of work with no unbounded call in the path.

Path one — the click redirect

1
Resolve the tracking code from process memoryEvery active tracking link is held in a per-process dict, refreshed on Postgres LISTEN/NOTIFY and re-synced every 60 seconds as a backstop. The redirect performs zero database queries. A cold miss falls back to a single indexed lookup and populates the cache.
2
Mint a UUIDv7 click_idTime-ordered, so it sorts into the index instead of scattering, and its embedded timestamp gives a free sanity check against click injection.
3
Append to a bounded in-process bufferNot an await on Redis. A deque with a hard cap; a background task ships it to the Redis Stream in pipelined batches every 50 ms. If Redis is down the buffer fills and sheds oldest-first — the redirect still succeeds.
4
302 to the platform destinationChosen by parsed User-Agent, with click_id appended to the store URL's referrer parameter for Android and carried in the deferred-link context for iOS.
5
Consumer persists in COPY batchesThe stream consumer accumulates up to 5,000 rows or 250 ms, then copy_records_to_table into today's partition, then acks. Crash before ack means redelivery, which the dedup key absorbs.

Path two — event ingestion

Authenticate by key prefix against a Redis-cached key record, verify payload size (256 KB hard cap, and a decompressed-size cap so a gzip bomb cannot be used to burn CPU), validate with msgspec against a struct rather than a Pydantic model, publish the batch to the stream, return 202. Target p99 under 15 ms for a 20-event batch. The endpoint never reads Postgres and never computes anything an analyst would recognize.

100k+

~5k

< 30s

click-to-queryable p95, from redirect to the row appearing in a rollup. Attribution resolves within the same window.

Read-path rules, enforced in code

  • Every analytics query requires an explicit date range; unbounded requests are rejected, not silently capped.
  • Maximum range 90 days without an export flag; export goes through a separate async job that writes to object storage.
  • statement_timeout = 15s on the analytics role, 2s on the tracker role. A slow query dies rather than holding a pooled connection hostage.
  • Redis cache with a 5-minute TTL on dashboard aggregate reads, keyed including organization_id so a cache key can never cross a tenant.
  • Query cost returned in a response header, so an expensive dashboard screen is visible before it is a production incident.
Accuracy

The correctness contract

An MMP's product is its numbers. Async ingestion, retries and offline SDK queues all mean at-least-once delivery, so exactly-once has to be produced at the write, by the database, not hoped for in the transport.

Attribution, precisely

Deterministic last-click only, in a strict precedence order — no probabilistic fingerprinting, as the original spec correctly insisted:

  1. Play Install Referrer carrying our click_id. Ground truth on Android; nothing overrides it.
  2. Explicit click_id handed to the SDK through a deferred deep link.
  3. Device-hash match — an exact gaid/idfa hash present at both click and install, within the window.
  4. Organic. If none of the above match, the install is organic. There is no fourth guess.

Default window 7 days for installs, 30 days for post-install events, configurable per app, and stored on every attribution row — so when someone changes the window, historical rows still explain themselves. Ties break to the most recent qualifying click by clicked_at.

Fingerprint fallback is a decision, not a default

The Lean section of the v1.0 spec suggests IP + device model + OS fallback for post-ATT iOS. That materially raises install match rate and is the technique Apple's rules prohibit for cross-app attribution; it also produces attributions that cannot be defended to a client who asks how a number was derived. My recommendation is to ship without it and let iOS be honestly SKAN-shaped. If commercial pressure forces it, it must be a per-app opt-in flag, recorded in attributions.method as probabilistic, and reported in a separate column in every dashboard — never blended into deterministic totals.

Proving accuracy rather than claiming it

  • A golden replay suite. A fixture set of click/install/event sequences — duplicates, out-of-order arrivals, clock skew, window edges, injection timing — replayed against a fresh database in CI, asserting exact expected attribution output. This is the regression net for every future change to the engine.
  • A daily reconciliation job. Counts accepted at the edge versus rows persisted versus rows in rollups, per app per hour, written to pipeline_audit. Any drift beyond the dedup rate alerts. Silent loss is the failure mode that kills trust in an MMP, and it is only detectable if you count both ends.
  • Published measurement definitions. What counts as an install, a session, an active user, a day boundary — written down once, in the app's timezone, and referenced by both the code and the sales deck.
Security

Tenancy, credentials, and the outbound edge

Three areas carry nearly all the real risk in this product: one tenant reading another's data, stored partner credentials leaking, and the postback engine being turned into a request forwarder. Everything else is standard hardening.

Multi-tenant isolation, twice

Application middleware resolves the active organization and scopes every query. Independently, Postgres row-level security enforces the same rule at the storage layer. The API connects as a role with RLS enforced and without BYPASSRLS; each request opens a transaction and sets the tenant for its duration.

ALTER TABLE campaigns ENABLE ROW LEVEL SECURITY;
ALTER TABLE campaigns FORCE ROW LEVEL SECURITY;

CREATE POLICY org_isolation ON campaigns
  USING      (organization_id = current_setting('mmp.org_id')::uuid)
  WITH CHECK (organization_id = current_setting('mmp.org_id')::uuid);

# and in the request scope — SET LOCAL, so it dies with the transaction
async with pool.acquire() as conn, conn.transaction():
    await conn.execute("SELECT set_config('mmp.org_id', $1, true)", str(org_id))
    ...

Four database roles, least privilege each: mmp_api (RLS-enforced, no DDL), mmp_tracker (INSERT on event tables only, 2s statement timeout), mmp_worker (RLS bypass, scoped to the tables it processes, used only by code that has no request context), mmp_readonly (analytics and BI tools). No service ever connects as owner or superuser.

The RLS + PgBouncer trap

In transaction pooling mode, a connection is handed to another request the moment your transaction ends. A tenant set with SET instead of SET LOCAL leaks into the next tenant's queries — a cross-tenant read with no bug in your query code. The shared pool helper must be the only place that sets tenancy, it must always use SET LOCAL inside an explicit transaction, and there must be a test that asserts a connection returned to the pool has no mmp.org_id.

S2S requests are signed over a canonical string of method, path, timestamp, and body digest; the server rejects a timestamp more than 5 minutes off, caches the nonce in Redis for that window to kill replays, and compares with hmac.compare_digest — never ==.

The outbound edge: SSRF is the sharpest risk here

Postback rules and webhooks are, by design, user-supplied URLs that our servers fetch. Unguarded, that is a proxy into the VPC and straight at the cloud metadata endpoint. The mitigation cannot be a naive hostname regex, because DNS can be rebound between validation and connection.

  • Resolve the hostname ourselves, reject any address in private, loopback, link-local, or metadata ranges (169.254.0.0/16 included), then connect to the validated IP with the original Host header — closing the rebinding window.
  • HTTPS only. Redirects disabled entirely. Response body read with a hard size cap and a 10-second total timeout.
  • Per-organization domain allowlist for postback destinations, defaulting to the known networks' domains.
  • All outbound delivery leaves through a dedicated egress security group with no route to internal services — a control that holds even if the application check is bypassed.

URL templates must not be a template engine

Postback URL templates take variables like {{click_id}}. Rendering those with Jinja2 hands anyone who can create a postback rule a path to server-side template injection and, from there, code execution. Substitution is a fixed allowlist of variable names against a dict, with every value URL-encoded on insertion. No engine, no expression evaluation, no attribute access.

PII and data governance

  • Raw IPs are never stored. Geo is resolved at the edge, then the IP is HMAC'd with a pepper that rotates daily and the original discarded. Rotation caps correlation to a single day.
  • Advertising IDs are hashed at rest and their rows dropped when the attribution window closes.
  • Consent is checked before processing, not after. Denied purposes strip fields at ingest, before anything is persisted.
  • Deletion is a real workflow: a request enqueues deletion across partitions, rollups and the postback log, and records completion in an append-only, hash-chained audit table.
  • Logs are structured and PII-free, with a redaction filter on the logger and a CI test that fails if a known-sensitive field name appears in a log call.

Baseline, automated

ruff, mypy --strict, bandit and semgrep gate every PR; pip-audit against the hash-pinned lockfile gates every build. A repo rule bans f-string SQL outright — asyncpg is parameterized-only, and dynamic ORDER BY goes through an identifier allowlist. Queue payloads are JSON or msgpack; pickle is banned in the codebase, which is the single largest reason to avoid Celery's defaults here. Containers run non-root with a read-only filesystem. Security headers and a strict CORS policy are set centrally, with the tracking endpoints carrying their own separate, deliberately permissive-but-credential-less policy.

Graduation triggers — review at each, don't pre-build for them

Read latency

Rollup-backed dashboard p95 over 500 ms with the query plan already correct → columnar analytics store.

Write pressure

Sustained ingest above 30k events/sec, or COPY batch latency rising with the backlog → partition by app as well as time, or shard.

Retention

Raw retention needed beyond 12 months at 1 B+/month → cold tier in object storage with an external query engine.

Residency

A first EU client asking where data lives → regional deployment, decided before signing, not after.

Gaps from the v1.0 review that this plan closes

The critical review in the original document flagged several launch blockers. Three of them are folded into the phase plan below rather than deferred: API versioning (a written policy with a 90-day deprecation window, in Phase 0, before any external integration), usage metering (a usage_rollup table from Phase 3, so billing data exists before billing does), and a postback sandbox (a test mode that fires against an internal echo endpoint, in Phase 9, so nobody sends test conversions to a live ad account). Raw data export lands in Phase 12. The cost model per million events is an input I need from you, not something I can decide — see Open decisions.

Phases

Revised build order

Thirteen phases, sequenced so that nothing depending on correctness is built before the mechanism that guarantees it. Run one phase at a time; type checks, security gates and the golden replay suite pass before the next one starts.
