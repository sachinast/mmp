# 13 — AI Specification

> **STATUS: NOT BUILT — and one part of it is a deliberate refusal, not a gap.**
>
> There is no machine learning anywhere in this platform. No model, no
> inference, no training data, no LLM, no vendor. The fraud subsystem that looks
> like the obvious home for it is rule-based **on purpose**, and that decision
> is documented in the code and in [FRAUD.md](../FRAUD.md).
>
> This document exists to record why, and to specify what would have to be true
> before that changes. It is a decision document, not a plan of record.

## Why fraud detection is rules, not a model

A trained classifier would very likely catch more fraud. It also could not
answer the question that follows every detection:

> *"Why did you stop paying us for these 40,000 installs?"*

A rule answers that. "97% of installs on this link converted more than seven
days after the click, across 1,200 installs — genuine traffic converts mostly
within the hour." A network that is told this can stop doing it, which is the
actual goal. A model score of 0.87 tells them nothing they can act on, and
detection that cannot be explained just moves the fraud somewhere less visible.

There is a commercial dimension too. This platform is a referee between parties
with money at stake. Its authority rests on every number being defensible. An
unexplainable accusation costs a partnership, and false positives are the
expensive error here — missing some fraud costs money that is already mostly
lost.

## Where ML would genuinely help

Recorded honestly, because the argument above is not "ML is bad":

**1. Threshold tuning per app.** The strongest candidate. Fraud thresholds are
global today, and a hyper-casual game and a banking app have very different
legitimate click-to-install distributions. Learning a per-app baseline and
flagging deviation from it is more accurate than one global number, and it stays
explainable: "this link's distribution differs from your app's own norm."

**2. Anomaly detection on a customer's own metrics.** Install volume collapsing
or revenue spiking is worth an alert, and nobody needs an explanation of *why*
an alert fired beyond the number that moved.

**3. Conversion value modelling.** SKAdNetwork gives six bits. Choosing an
encoding that captures the most information about revenue and funnel stage is a
genuine optimisation problem, and getting it wrong is invisible.

**4. Bot classification from user agents.** Currently a substring list. A
classifier would generalise better — though it must stay on the *flagging* side,
never blocking.

## Requirements if any of this is built

Non-negotiable, and they follow from the rest of this platform's design:

1. **Never on the hot path.** The redirect is 2.4 ms and does no database work.
   Inference belongs in the worker or a sweep.
2. **Never the sole basis for an accusation.** A model may prioritise
   investigation or tune a threshold. A rule with a stated number makes the
   finding.
3. **Reproducible.** Fraud findings get argued about months later. A model
   version must be recorded on every finding, and an old finding must be
   re-derivable from stored inputs — the same standard the pure-function rules
   already meet.
4. **No cross-tenant training without explicit consent.** Training on one
   advertiser's data to score another's is a data-sharing arrangement, whatever
   it is called internally, and customers must agree to it in writing.
5. **No personal data as features.** The platform hashes advertising IDs and IPs
   at the edge and discards the raw values. A model must not become the reason
   to retain what was deliberately thrown away.
6. **Flag, never discard.** The existing rule — a flagged install is still
   attributed and still counted — applies unchanged.

## What is explicitly rejected

- **LLMs anywhere in the measurement path.** Non-deterministic output has no
  place in numbers an advertiser is invoiced on.
- **Probabilistic attribution by any name.** Whether the model is statistical or
  learned, an attribution that cannot be explained is one that should not be
  charged for. See [01](01-prd.md).
- **Any feature requiring a cross-app identity graph.**

## Next step

Item 1 (per-app threshold tuning) is the only one with a clear payoff and no
conflict with the principles above. It needs labelled data that does not exist
yet — the fraud thresholds currently in production are reasoned, not measured.
Collecting that labelled data is the prerequisite, and it is not a modelling
task.
